## 2. 固定审计发现与执行项

以下锚点属于审计基线；执行时核对当前路径/行号。Verified Facts 是源码、配置和既有测试中实际读取到的行为；攻击步骤、时间向量及运行影响属于 Inferences/Hypotheses，须由回归验证。整改要求是 Recommendations/验收约束；cluster 能力和未运行结果属于 Unknowns。不得把静态推导写成实际运行的攻击结果。

### R1 — P1：阻断未上链计划绕过 hidden provenance

位置：

- [provenance-service:50–71](https://github.com/build-on-sol/Provena/blob/203fd320c64fb518cbe3651a6fee54e1c293b92a/services/provenance-service/index.ts#L50)：任意已认证 creator 可基于已登记目标生成并持久化 ATTESTED_PLAN。
- [provenance-service:79–103](https://github.com/build-on-sol/Provena/blob/203fd320c64fb518cbe3651a6fee54e1c293b92a/services/provenance-service/index.ts#L79)：reveal 只检查新计划 creator/authority，随后遍历祖先；creator 也可取得完整 payout vector。
- [server:79–87](https://github.com/build-on-sol/Provena/blob/203fd320c64fb518cbe3651a6fee54e1c293b92a/services/server.ts#L79)：普通 signed HTTP 请求即可触发。
- [server.test:176–186](https://github.com/build-on-sol/Provena/blob/203fd320c64fb518cbe3651a6fee54e1c293b92a/services/server.test.ts#L176)：已有测试在计划未确认、无经济事件时允许全链 reveal。

静态推导的复现步骤（待运行确认）：服务已配置 Rights signer，A→B→C 正常登记。攻击者 X 以 C 为 parent 请求 D 的计划，再以 D.creator 身份 reveal D，得到 D→C、C→B、B→A。无需链上 D、Rights 交易联署或付款。

协议依据：执行契约 §14 禁止普通查看者通过平台直接沿链读取 C→B→A；§61 在价值事件之后允许全链 reveal，并要求 SDK 验证 commitment。

整改要求：

- 把披露资格绑定真实、已确认的链上节点及对应价值事件。仅有 signed wallet、ATTESTED_PLAN、用户自报交易/事件、未验证缓存或单独 CHAIN_VERIFIED 标签均不足。
- 保留已有 creator/authority 权限边界，不自行添加公开查祖先、购买者或 admin 的新读取角色。平台内部已披露的 Rights authority 知情边界与普通用户接口分别核对。
- 不能只禁用未上链计划：新 D 即使创建成功，在没有符合协议条件的价值事件时也不能借自身身份读取 C 的既有祖先。
- 复用既有 chain reader、node/epoch/receipt 或经验证的 finalized 交易证据；校验 program owner、账户类型、node/content 归属及确实成功的正金额经济行为。不新增链上 parent 指针或平行金融账本。
- 连同 payoutProof 的完整向量披露和相关响应一起审查；保留权益人取得自身 leaf/proof 的必要路径，不能通过第二个接口返回同样受保护的祖先信息。
- 不凭本任务增加最低支付门槛或新的产品权限。如果具体读者/事件归属无法从契约和既有边界确定，先保持拒绝披露并记录明确 policy gap，不自行放开读取。

验收：signed HTTP 层和 service 层均拒绝 X 的计划→reveal 攻击、已上链无经济事件变体、伪造/外来 node 或未 finalized 经济证据；符合既有权限与真实价值事件条件的 reveal 成功且 SDK commitment 校验通过；请求自己的 Merkle leaf/proof 仍可用。

### R2 — P2：零收入争议提前解决后继承原窗口

位置：[lib.rs:743–771](https://github.com/build-on-sol/Provena/blob/203fd320c64fb518cbe3651a6fee54e1c293b92a/programs/content_rights_protocol/src/lib.rs#L743)。

静态时间向量（START=1_000_000，DAY=86_400）：

- D0 零收入开启 case：cutoff=1_604_800（D7）。
- D1 holding 入账：epoch.deadline=1_604_800，但 Content.normal_deadline 保持 0。
- D3 Independent。
- D3 新 post-review epoch 入账：当前实现设置 deadline=1_864_000（D10），旧 epoch 仍 D7。

这是新周期提前开始的语义偏差；没有发现旧本金被延长或盗取。执行契约 §19.1 要求旧窗口结束后才能启动新的独立周期，§26 禁止因提前解争议重新获得完整七天。

整改要求：

- 复用现有 Content/RevenueEpoch/SimilarityCase 账本，使未结束内容周期的期限在首次 holding 入账和提前解决后保持可继承。
- 最小方向是记录/继承有效 cutoff；具体处理由当前代码决定，不能无条件把所有未来收入永远绑定已结束 case 的旧截止。
- 增加 SBF 交易回归，验证上述 D0/D1/D3 序列的新旧收入均截止 D7。
- 一并核对零收入 case 提前解决后才首次入账、Independent/Derivative、不同 node/mint、TIP/SALE；按契约解释并记录预期，不能通过另开 epoch 重置尚未结束的周期。
- 旧窗口结束后的真实新周期仍可开始；晚解决依旧自动退出并受 48h 冷却；部分 claim 和再次入账不刷新既有 deadline。

### R3 — P2（条件化）：transaction v1 兼容与索引进度

位置：[indexer:116–141](https://github.com/build-on-sol/Provena/blob/203fd320c64fb518cbe3651a6fee54e1c293b92a/services/indexer/index.ts#L116)、[server:143–150](https://github.com/build-on-sol/Provena/blob/203fd320c64fb518cbe3651a6fee54e1c293b92a/services/server.ts#L143)。

当前 getTransaction 固定 maxSupportedTransactionVersion:0。目标 cluster 接受 v1 时，相关成功交易会在 checkpoint 更新前触发异常；poller 持续重试同笔，后续事件无法索引。getSignaturesForAddress 依据 accountKeys 查询，所以相关交易不必真正调用 Provena。

本轮未实测 devnet 是否启用 v1；不得报告“devnet 已发生”。依据为 [官方地址查询文档](https://solana.com/docs/rpc/http/getsignaturesforaddress) 与 [Anchor 0.32.2 发布说明](https://www.anchor-lang.com/docs/updates/release-notes/0-32-2)。

整改要求：

- 执行时核对当前官方客户端兼容说明；在现有 RPC adapter 中支持目标交易格式和事件读取。
- 仅把版本上限改成 1 不足以证明旧 web3.js/Anchor 能正确解析。若需依赖调整，只改经过验证的最小客户端依赖集合及 lockfile；不默认升级 Rust、Anchor 合约、Agave 或迁移整套 SDK。
- 回归覆盖 legacy、v0、v1 成功交易，失败交易、仅引用 program 的无事件交易、foreign logs、重复事件、分页/重启 checkpoint 和暂时 RPC 错误。
- v1 成功交易前后的有效事件均能读取且不重复，checkpoint 正确推进。不能通过静默跳过未知交易或伪造 checkpoint 丢弃金融事件来让测试通过。
- 无法支持某格式时明确记录 capability gap 与受影响范围，保留可恢复证据；不把不完整投影显示为已同步。链上 custody 和 finalized receipt 直读不得因此改成依赖 indexer。

### R4 — 验证缺口：补足 Token-2022 真实经济 CPI

位置：[security.rs:1850–1918](https://github.com/build-on-sol/Provena/blob/203fd320c64fb518cbe3651a6fee54e1c293b92a/programs/content_rights_protocol/tests/security.rs#L1850)。该测试验证 mint/policy/vault 初始化和 freeze authority 拒绝，但没有 Token-2022 tip/purchase/claim/fees 的成功转移；其他经济 fixture 使用经典 SPL Token。

整改要求：

- 复用 LiteSVM/SBF fixture，以已批准、无 freeze authority、无扩展的 Token-2022 mint 执行真实 transfer_checked。
- 覆盖 tip→claim、purchase→content-scoped AccessReceipt→claim、Derivative 计提→withdrawProtocolFees，以及 safeguard→request→48h 后 claim。
- 每条路径检查真实 source/vault/destination token balances、epoch paid/fees/gross 与 asset user_liability/earned_fees 守恒；测试失败交易的原子回滚。
- 保留 SPL Token 同类路径和 wrong mint/program/owner/destination、超额费用、重复领取、receipt 重放、freeze/扩展 mint 拒绝。
- 不能仅把 fixture 账户 owner 改为 Token-2022 然后检查初始化，也不能只测数学函数。不得放开未审计扩展或改弱 whitelist 来通过测试。

### R5 — 服务可用性：pending staging 不得永久抢占身份

位置：[content-service:74–105](https://github.com/build-on-sol/Provena/blob/203fd320c64fb518cbe3651a6fee54e1c293b92a/services/content-service/index.ts#L74)、[server:66](https://github.com/build-on-sol/Provena/blob/203fd320c64fb518cbe3651a6fee54e1c293b92a/services/server.ts#L66)。

普通 signed staging 会立即永久登记本地 canonical fingerprint，无链上提交/Originality 授权验证，也没有释放路径。知道正文的攻击者可抢先 stage，使真正作者无法随后使用服务。该风险影响服务入口，不会授予攻击者链上 fingerprint 所有权。

整改要求：

- 将未确认 staged artifact 与链上已成立身份区分；未获确认的本地草稿不能成为跨作者永久占位的依据。
- 复用现有签名认证、chain reader 和持久化；保留链上全局唯一性。选择最小 pending/确认或受控回收方案，不新增版权裁判/公共覆盖接口。
- 已确认内容、付费 ciphertext/keys、真实购买资格和已签署 commitment 不能被回收、覆盖或重新绑定给另一个钱包。
- 回归：X 抢先 stage 但不提交链上，合法作者仍能准备自己签名的提交；真实链上 duplicate 仍拒绝；未授权钱包不能删除/覆盖他人已确认 artifact；并发和服务重启不造成 ownership 或 key 混用。
- 不把 pending 的风险检测/本地索引包装成已批准链上内容；更新必要的服务状态说明和 tests。
